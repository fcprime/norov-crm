# Оновлення CRM 0.13 — Telegram-шаблони й оформлення таблиць

## Що змінилось

- У картці кожного клієнта є редактор Telegram-звіту: окремо щоденний і щотижневий шаблони.
- Можна змінювати текст, emoji, порядок показників, прибирати рядки, вставляти змінні кнопками.
- Приклад у редакторі використовує демонстраційні цифри. «Переглянути звіт» після збереження показує фактичні дані Meta без запису й надсилання.
- Існуючі клієнти зберігають стандартний текст, доки ти не зміниш шаблон.
- Google отримує числа. Оформлення наявних аркушів, включно з валютами, відсотками, кольорами, шрифтами й розмірами, не перезаписується.
- Новий службовий аркуш «Meta — щодня» отримує початкове оформлення лише при створенні. Його подальші зміни вручну зберігаються.

## Встановлення

1. Заміни файли проекту файлами цієї збірки. Збережи свої `.env.local`, `.env.functions`, Google JSON та `.git`. Не завантажуй секрети в GitHub.
2. Supabase → SQL Editor: відкрий файл `supabase/migrations/20261009070544_telegram_report_templates.sql`, скопіюй увесь SQL і виконай. Це додає лише колонку шаблонів. Старі налаштування й таблиці зберігаються.
3. У терміналі в папці проекту виконай:

```bash
npx supabase functions deploy client-reports --project-ref ltdxqqukbsbxwnjxbuti
```

4. Завантаж оновлені файли у свій GitHub-репозиторій. Дочекайся успішного оновлення Netlify й онови сторінку CRM.

Cron, Vault, токени, ключ шифрування й розклад змінювати не потрібно. Якщо версія 0.12 уже встановлена, виконуй лише новий SQL з пункту 2.

## Редактор Telegram-звіту

Картка клієнта → Автоматичні звіти → Текст Telegram-звіту.

Обери щоденний або щотижневий шаблон. Наприклад, для клієнта з лід-формами:

```text
📊 {{name}}
📅 {{period}}

👥 Ліди: {{leads}}
💰 Витрати: {{spend}}
🎯 Ціна ліда: {{cpl}}

Покази: {{impressions}}
Кліки: {{clicks}}
CTR: {{ctr}}
```

Збережи звітність. Потім обери тип тестового звіту й дату та натисни «Переглянути звіт».

- `{{name}}` — назва клієнта з CRM.
- `{{period}}` — день або період звіту, формат YYYY-MM-DD.
- `{{date_from}}`, `{{date_to}}` — межі періоду.
- `{{leads}}`, `{{messages}}`, `{{impressions}}`, `{{clicks}}` — кількості.
- `{{spend}}`, `{{cpl}}`, `{{cpc}}`, `{{cpm}}` — суми з фактичною валютою Meta. Не додавай до них ще один знак валюти.
- `{{ctr}}` — відсоток уже зі знаком %.
- `{{currency}}` — код валюти, наприклад USD або PLN.

Щоб приховати переписки, видали весь рядок із `{{messages}}`. Це не змінює підрахунок лідів і запис у Google.

«Стандартний шаблон» відновлює лише поточний шаблон; зміни потрібно зберегти. Шаблон має до 3000 символів; готове повідомлення — до 4096. Звіт надсилається звичайним текстом: HTML і Markdown-розмітка не обробляються. Для тестового надсилання система додає «🧪 ТЕСТ».

Для тижневого тесту вибрана дата означає тиждень надсилання: звіт буде за понеділок–неділю попереднього тижня. Можна обрати сьогодні. Період поточного аркуша має охоплювати всі дні, які потрібно записати.

## Формули й валюта в Google

Для нових щоденних рядків рекомендується прибрати формули CPL, CPM, CPC й CTR, адже система вже обчислює їх із даних Meta. Для CapitalJob це D, E, G, I, починаючи з незаповнених днів. Попередні дні та формули «Загалом» залишаються.

Якщо хочеш зберегти формули щоденних рядків, залиш відповідні поля колонок порожніми в CRM. Інакше захист вважатиме рядок зайнятим і пропустить його.

Система не конвертує валюту. У шаблоні Google ти сам задаєш валютний формат колонок D, E, G, J, відповідний кабінету: $ для USD, zł для PLN тощо. CTR у колонці I повинен мати відсотковий формат. Якщо колонка має неправильну валюту, змінити лише формат недостатньо для конвертації — потрібен правильний шаблон для цього кабінету.

Рядок за 08.10, який попередня версія вже оформила як USD, автоматично не змінюється. Виділи D16, E16, G16 та J16 і застосуй той самий валютний формат $, що в попередніх рядках (можна скопіювати лише форматування з відповідних клітинок рядка 15). Нові записи зберігатимуть оформлення своїх клітинок.

## Перевірка

Збережи шаблон, переглянь фактичний звіт за 08.10.2026. Уже заповнений день у вибраному аркуші буде пропущений — це захист від перезапису. Не очищай його лише заради перевірки оформлення. Наступний порожній день буде записаний автоматично за чинним розкладом.

Локально перевірені: збірка React/TypeScript, типи серверної функції, підстановка змінних і валют, щотижневі суми, обмеження шаблонів, запис чисел без зміни форматів, захист формул і повторного запису, попередні перевірки JWT. Розгортання й новий SQL у твоєму Supabase потрібно виконати за інструкцією вище.
